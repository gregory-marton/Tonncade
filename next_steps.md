# Next Steps: Future Feature Ideas

At this point, issues should be tracked using GitHub's issue tracker,
so this document is for upcoming feature ideas.

- **Grand-staff notation for Melody/Compose, MusicXML as the canonical format** (design in
  `docs/melody-notation-design.md`, not yet started): render the current song (or Random's
  generated sequence) on a real grand staff with note names/octaves underneath, with measure
  barlines spanning the staff, the name/octave row, AND the existing note-timeline below it as one
  connected block. VexFlow gets vendored directly (NOT Smoosic -- actually downloaded and
  inspected; Smoosic's own published bundle is a 25MB unminified dev build wrapping its entire
  desktop application, not embeddable at this app's scale -- see the doc). Bundled songs move from
  MIDI to MusicXML as their authored format (exact notated rhythm/key/time-signature, nothing
  inferred); Compose's Save moves off `writeMIDI()` onto real MusicXML export; Compose gains
  staff-click editing (click to add, drag a notehead to re-pitch/resize) alongside its existing
  Tonnetz-tap, routed through the same mutators so `js/undo-stack.js` (#17) doesn't care which
  surface an edit came from. Key/time-signature become an explicit, changeable-mid-piece setting
  (a `{time, value}` track, same shape MusicXML itself uses), fed into `Tonnetz.getNoteName` so the
  Tonnetz's own labels spell notes correctly for whatever key is active, not always sharps. Full
  MusicXML feature-coverage decision (repeats + variant endings expanded at import, ties
  supported, grace notes and glissando flagged as needing their own follow-up design passes
  beyond notation rendering, pedal/dynamics/lyrics/tab explicitly excluded) and the music21
  question (kept as an explicit fallback, not adopted -- there's a real argument the lightweight
  hand-rolled quantizer/speller/measure-inference is closer to correct for this app's actual
  audience, not just cheaper) are both in the doc, not repeated here.
- **Compose mode has no live MIDI hardware input routing** (docs/invariants.md INV-32's actual
  invariant is "live MIDI hardware input is supported in every mode" -- Compose is currently the
  one exception; `js/midi-input.js`'s `MidiInput.handleNoteOn` has a branch for every OTHER mode,
  including Life, but none for `App.currentMode === 'compose'`). The natural mapping: while
  recording, a MIDI note-on should record a note the same way `ComposeMode.tapCell`'s recording
  branch does (or `recordTouch`, for chords -- `MidiInput` already buffers near-simultaneous
  note-ons the same way Blast's chord handling does, see INV-32); while not recording, it should
  probably just preview-play the note (matching a tap on an unselected empty cell) rather than
  mutate the piece. Needs its own design pass on exactly which existing Compose method(s) a MIDI
  note-on should call — not scoped further here.
- **#28 Device-rotation as a viewing angle, not just a resize**: in Gravity mode, rotating the device correctly keeps "higher pitch = up" fixed on screen, since falling pieces need a stable notion of "down" — that stays as is. In Blast, Snake, Melody, and Sandbox, none of which have gravity-driven mechanics, device rotation could instead let the Tonnetz visually rotate along with the phone (0°/90°/180°/270°), so physically turning the device reveals a different rotated view of the same fixed lattice, while controls/stats and — critically — each hex's in-grid note-name label counter-rotate individually to stay upright and legible regardless of the overall grid's rotation. Needs a real device-orientation-angle read (`screen.orientation.angle` or equivalent) with early cross-browser verification, since this API has had inconsistent behavior on iOS Safari historically.
- **#29 i18n export**: any English-language UI text (button labels, status messages, instructions) is a future translation cost and will impact appearance and spacing when translated. Strong bias against adding more text where a non-linguistic alternative (icon, symbol, color) would work just as well. Some text is likely unavoidable — chord type names ("Major 7th", "Sus4", etc.) and note names use standard music-theory notation that doesn't have an obvious non-linguistic substitute, and inventing one isn't something to do without real music-theory expertise informing it. ~~Scope: catalog existing English strings across the UI as a review list, and keep this bias in mind for new features going forward.~~ Done: catalog below. The next concrete step, not yet started, is to separate all such strings into their own js file organized as a dictionary with a primary language key and secondary role key, so it will be easy to augment with another language.

  **Catalog** (swept `index.html` + every `js/*.js`, grouped by how replaceable each group looks — no code changed here, this is inventory only):

  - **Essential, no obvious non-linguistic substitute** — standard music-theory notation, matches the bias doc's own exception: chord-guide result names (`Major Triad`, `Minor 7th`, `Dominant 7b9 (shell)`, `Quartal Stack`, and ~15 others), note names (`C`/`C#`/... from `Tonnetz.getNoteName`), the octave-qualified names and Hz readout added tonight (INV-25).
  - **Structural labels, plausibly icon-replaceable** — the biggest bucket, and the best-leverage target if this audit turns into real work later: mode names (`Sandbox`/`Melody`/`Snake`/`Blast`/`Gravity`), `Pause`/`Resume`/`Restart` (every mode redeclares these three independently — Gravity, Snake, Blast, Melody's "Restart Game" — a single shared icon set would also dedupe four near-identical implementations), `Difficulty:`/`Easy`/`Medium`/`Hard`, `Play Melody`/`Stop Preview`, `Place/Pick up`/`Place Piece`, `Lines:`/`Best:`/`Score:`/`Current Streak:`/`Longest Streak:`/`Speed:` (stat labels — a small glyph beside a bare number reads fine cross-culturally). The three MIDI-folder button states added tonight (`Choose MIDI Folder`/`Change Folder`/`Reconnect Folder`) belong here too — added without applying this bias, since the feature itself was the immediate priority; worth revisiting together with the rest of this bucket rather than one-off.
  - **Longer prose, NOT easily icon-replaceable** — instructional/status text where the actual information is inherently verbal, not a good audit target: the desktop-only "Keyboard Play Controls" block (`index.html` ~131-162, maps physical key rows to lattice regions — genuinely needs words), Melody's status-line prose (`Listen to the notes...`, `Correct! Go ahead! (2s timeout)...`, `Oops! Let's listen again...`, etc. — timing-sensitive coaching text), the three `alert()` error dialogs (MIDI parse failures, Gravity's game-over line count). Lowest priority: even in a fully localized build, these would just get translated as prose, not redesigned into icons.
  - **Accessibility-only** (`aria-label`/`title` attributes: "Connect a MIDI keyboard," "Rotate the Tonnetz view," "View source code on GitHub," the D-pad direction labels) — not visible UI text at all, so out of i18n scope in the usual sense, but still a future translation surface if the app ever ships a locale switcher (screen readers need translated labels too).

  No changes made — this is the review list the original scope asked for. Turning any bucket into actual icon replacements is separate, real design work (which symbol reads as "pause" without ambiguity across cultures is not a decision to make solo), not something to fold into this catalog pass.
- **#39 Easy/Medium/Hard difficulty presets for Blast and Gravity**: a difficulty selector that swaps which piece set is in play — Easy uses only smaller pieces (1-, 2-, and 3-ominoes) and in gravity has click-to-drop for each piece, Medium mixes smaller and the current full-size pieces and has click-to-drop, Hard is today's existing experience unchanged. In gravity, easy does not ever get faster, and medium gets faster logarithmically, not linearly. Not yet designed: where the selector lives in the UI.
- **#46 Melody mode: better support longer songs**:
  - Consider noting the errors visually without interrupting the student's playback.
  - 2s may not well support some learners, so this should either be adjustable or perhaps better -- self adjust with something like exponential backoff? If I'm hunting for and trying to remember the next note, perhaps visually highlighting or bouncing it would be more helpful than starting over. There is a lot of pedagogical design here to explore.
    - **Error tolerance**: past some difficulty threshold, forcing an exact-match full redo on every wrong note becomes counterproductive. Instead, tolerate a level of errors within a practice pass, track *where* in the song they happen, and surface that (e.g. "you tend to miss around here") to guide practice — rather than resetting progress on every mistake. Same underlying theme as the notation plan's grace-note handling (`docs/melody-notation-design.md`) -- both are about `handleUserInputNote`'s matching becoming tolerant/flexible instead of a strict linear exact-compare -- worth designing together rather than twice.
  - **Pedagogical redesign** Many songs are complex, with chords, or intended for a left and right hand, for example. This interacts differently with different inputs, so now that we support midi controls, someone playing an actual keyboard will have a very different experience of these than someone playing their mobile screen. Is it possible to auto-simplify for early practice, or separate hands, etc. The notation plan's grand staff (`docs/melody-notation-design.md`) already splits by register into two staves as a byproduct of engraving -- not the same thing as a real independent left/right-hand voice split, but worth checking whether it's close enough to build on rather than treating hand-separation as a fully separate problem.
- **#30 Alternate mathematical tuning system + selector** (farther future, nebulous): add a second mathematical backing for the grid's frequencies — an alternative to the current Tonnetz interval mapping (`Tonnetz.getMidi`: p:+7/q:+3 semitones for Standard tuning, p:-3/q:+4 for Gravity) — with a UI selector to switch between tuning systems. Prompted by an external conversation the user had exploring the idea (https://chatgpt.com/share/6a5ba607-d5e0-83ea-81c5-1796ca67c828); not yet read into or incorporated here, no design decisions made.
- **#50 Sandbox (and perhaps Melody) should reach the full range of human hearing, not just a piano's range**: today Sandbox's board (`Board.radius = 5`) covers MIDI 25–95 (34.6Hz–1975.5Hz, ~5.8 octaves) — comfortably inside standard 88-key piano range (MIDI 21–108, 27.5Hz–4186Hz), so the board itself is the current bottleneck, not audio playback. But `Synth.playNote()` (`js/synth.js:72-76`) silently octave-wraps any non-harmonic note outside MIDI 21–108 back inside that range — a leftover from when the piano range was a reasonable assumption. If the board is later widened to actually reach toward the ~20Hz–20kHz range of human hearing (roughly MIDI 15–135), that clamp would quietly defeat the whole point by wrapping the extreme notes back into piano range before they ever reach the speaker. So this is two changes together: (1) widen the playable board — larger `Board.radius` and/or a wider-interval axis mapping — so more extreme pitches are reachable, and (2) remove or widen the `Synth.playNote()` clamp to let those pitches actually sound, understanding that very low/high notes won't be audible on hardware that can't reproduce them (that's a real physical limit, not one to also enforce artificially in code). Not yet designed: how far to widen the board (a literal 20Hz–20kHz target is extreme and would make most of the grid inaudible on typical speakers), and whether the same change should apply to Melody mode's target range.
- **Snake portrait board far too small — shape-aware fit (INV-43)**, follow-up: `Render.fitBoardShapeAware` shipped for Snake portrait; not yet extended to Snake landscape (its D-pad is full-height left/right columns there — a different geometry), nor generalized to a reusable per-mode chrome-rectangle model. Both are reasonable future consolidations if another mode needs shape-aware fitting.
- **Boards don't fill the screen (pannable-mode letterbox), follow-up**: the "Random taps" exploratory test still soft-fails on some wide/short and portrait scenarios (tonnetz-share below floor) — needs a look to confirm whether those are genuine remaining fill gaps or measurement artifacts of the soft-assertion sweep; folded into #76's investigation. Gravity's desktop under-fill (scale=1 vs Blast 1.25/Snake 1.15, ~17% wasted height, plus inherent side-margins for a tall board in a wide container) was NOT changed by the original fix — a separate, smaller restricted-mode tweak.
- **Pannable modes on narrow mobile portrait don't fill (Melody/Compose)**: found via the screenshot fixture. On mobile (≤767px) `#tonnetz-svg` gets an absolute-inset CSS rule (INV-40) whose `--chrome-inset-*` are only maintained by the restricted modes, so a pannable mode falls back to fixed literal insets that shrink its board (Melody drawer-closed at 348×966 stays small instead of filling). Compose is worse in portrait because its tall controls stack (Choose Folder / tempo / grid / Record-Play-Undo-Clear-Save / stats) dominates the width, leaving only a sliver for the Tonnetz — "can't really see the Tonnetz" at 406×658. Needs a mobile-portrait layout pass for the pannable modes: either scope the INV-40 inset CSS to the restricted modes and give the pannable board the full container below its own (full-width) top controls bar, or set `--chrome-inset-*` correctly for pannable modes. The desktop leftover-inline-SVG bug (restricted modes stranded at a stale mobile box) is already fixed (`Render.fitContentBox` clears inline on its desktop early-return, INV-45); this is the remaining, mobile-only piece. **Gets more pressing, not less**, once the notation plan (`docs/melody-notation-design.md`) adds a grand-staff view stacked above this same timeline in these same two modes — worth handling this fill problem before or alongside that, not after.
- **Rotation-aware board fit for restricted modes** (filed from the same conversation as the item above): a regular hexagon's bounding-box aspect ratio varies continuously with rotation (empirically 0.876 at 30°, 1.141 at 0°/60°, for Snake's radius-7 board), so `fitContentBox`'s current rotation=0-only fit isn't necessarily the best-fitting angle for a given viewport's aspect ratio. Does NOT apply to Gravity (its render is hard-locked to 0° — falling pieces have a fixed axial "down," independent of viewing angle). Snake and possibly Blast could actually use auto-rotation; for Snake specifically, the D-pad's own button-to-direction mapping would need to rotate correspondingly to stay intuitive — a real design question, not just a rendering tweak. Related to #28 (device rotation as viewing angle). Not yet started.
- **Sidebar/controls default too large relative to the Tonnetz at tablet-ish viewport sizes**
  (surfaced investigating the browser-zoom fix, INV-53): reported live on ChromeOS at roughly
  tablet size, where the DEFAULT (no zoom at all) already shows less Tonnetz and larger controls

- **Compose: extend/overdub recording**: two related gaps raised after chord entry landed. (1) Resuming a stopped recording currently restarts its clock at 0 (`recordStartTime` resets unconditionally in `startRecording`), so there's no way to "add the next 4 measures" onto an existing take without it overlapping the start. (2) Overdub/layering: re-recording separate takes anchored to the *same* start point, then merging them into one note list, is a real mouse-compatible path to chords (one voice per pass, merged after) since a mouse can never produce simultaneous input the way multitouch can. Needs its own design pass (is layering a UI toggle? does merge just flatten to one list on save, or keep layers distinguishable? how does Undo interact with a layer boundary?) before implementation -- not yet started. Same general area (Compose's recording-session model) as the notation plan's explicit key/time-signature-change track (`docs/melody-notation-design.md`) -- worth checking whether resuming/overdubbing a recording and inserting a key/meter change mid-recording end up wanting the same underlying "session timeline" concept before designing either in isolation.
- **#53 Compose mode: link out to an external MIDI editor for rhythm-precision work** (follow-up to #52/task #64): Compose deliberately doesn't build in-app timing-editing (nudge buttons, a timeline) -- a rough recording is cheap to re-record, and real rhythm precision is better served by a dedicated tool working directly on the saved `.mid` file. **Signal** (`github.com/ryohey/signal`, hosted at signal.vercel.app) is a candidate: an in-browser, apparently GPLv3-licensed piano-roll MIDI sequencer, the closest match to "same kind of environment as this app" among the options discussed. Not yet verified firsthand. A true one-click hand-off (opening Signal already loaded with the file) likely isn't achievable anyway -- cross-origin restrictions mean a plain link can't inject a File/Blob into another origin's page, and our saved file isn't at a fetchable public URL (it's a local File System Access folder handle or a downloaded blob) -- so any link would just open Signal and the user re-uploads the file themselves. **Blocked on Gregory personally trying Signal with his own saved `.mid` files first**: confirm the license is actually as understood, and confirm the re-upload workflow is actually palatable, before committing to adding the link. **Worth re-reading once the notation plan lands**: that plan gives Compose real in-app notation editing (click to add a note, drag a notehead to re-pitch/resize) -- which is exactly the kind of "in-app timing-editing" this item says Compose deliberately avoids in favor of an external tool. Either this item's premise needs revisiting, or the notation plan's editing scope needs to explicitly stay short of rhythm-precision nudging -- not both assumed true at once.
